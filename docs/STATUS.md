# Status — 2026-11-23

ATLAS 0.1.0 is a working Phase 0 / Phase 1 foundation. The requested first milestone is demonstrated: three different videos are generated by changing JSON configurations without modifying the engine.

## Implemented and exercised

- Installable local Python package and CLI: doctor, schema, validate, render, verify, jobs.
- Version 1.0 renderer-independent Pydantic IR, strict unknown-field rejection, safe identifiers, finite bounded numbers, timeline/reference/aim validation and pre-render revalidation.
- Seven reusable primitive types, materials, ground/world settings and deterministic scatter with within-group center spacing.
- Integer-frame location/rotation/scale animation, linear/Bezier/constant interpolation, animated camera position, fixed/entity tracking and optional depth of field.
- AREA/SUN/POINT lighting; CPU Cycles and Eevee subprocess rendering; editable .blend files and PNG sequences.
- FFmpeg H.264/yuv420p assembly, frame count/dimensions/fps/stream-and-container duration checks, full decode before success.
- Structured host logs, per-frame renderer logs, unique job directories, atomic project/manifest writes, transactional job history and read-only history listing.
- Reproduction manifests with effective/resolved configuration, source/project/output hashes, seed, software versions, settings, timings and diagnostics.

## Verification evidence

- Full suite with `ATLAS_INTEGRATION=1`: **53 passed, 1 skipped in 28.61 s**. The single skip is a file-symlink escape test because Windows denied symlink creation. Non-symlink path traversal and read-only database tests passed.
- Four real integration tests: CPU Cycles pipeline, Eevee pipeline, final-manifest failure injection, and seven-primitive/transform/camera/DOF verification. Saved scenes are reopened in separate Blender processes.
- A fresh environment installed the built wheel and dependencies from local wheel files. The installed package was imported from `site-packages` outside the repository and produced a verified CPU-rendered MP4.
- Three example MP4s: 72 frames each, 24 fps, exactly 3 seconds, H.264/yuv420p; two 480x270 landscape videos and one 270x480 portrait video. All passed independent final-code CLI verification. Representative frames were inspected.
- Independent code review found finalization ordering, container duration, read-only history and aim-validation issues. All were reproduced with failing regression tests and fixed. Extreme numeric input and streaming video hashing were also addressed.

## Limits and incomplete functionality

No third-party asset ingestion/license registry, character rigs, semantic interactions, physics, audio, multi-shot timeline, action planner, queue/resume/cache system, dashboard, Unity backend or arbitrary natural-language generation exists yet. No empty placeholder modules claim these features.

One scene/camera per project; integer fps only; Euler animation; no quaternion/root-motion system. Scatter separates XY centers within each group, not actual collision geometry. Camera validation catches directly specified degenerate static aim, but does not solve continuous-path crossing, moving-target coincidence or obstruction. Visibility diagnostics inspect centers only.

Hard process termination or disk failure can leave unfinished metadata; no automatic stale-job reconciliation or resume. Completed intermediate files are retained; rerun into a new job for manual recovery. SQLite and JSON do not form one transaction. Rendering is not an OS sandbox. Linux/macOS and other Blender releases remain unverified. Preview sampling noise is visible. Peak memory and final-resolution benchmarks remain unmeasured.
